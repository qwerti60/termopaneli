# План разработки приложения

## 1. Текущий статус

### Уже сделано

- Регистрация и авторизация пользователя.
- Подтверждение телефона через SMS-код в логике приложения.
- Временный режим без реальной отправки SMS: используется тестовый код `123456`.
- Проверка пользователя в БД после ввода кода:
  - если пользователь есть, выполняется вход;
  - если пользователя нет, открывается регистрация.
- Сохранение токена после успешного входа/регистрации.
- Проверка сохраненного токена при запуске приложения, чтобы не требовать повторную авторизацию.
- Переход на Telegram-канал при регистрации.
- Каталог термопанелей загружается и отображается через API.
- Подготовлены примерные каталоги откосов и дополнительных элементов в `docs/catalogs`.
- Добавлен SQL для таблицы `catalog_materials` и стартовой загрузки откосов/дополнительных элементов.
- API каталога подготовлен к выдаче категорий `panel`, `slope`, `corner`, `grout`, `ebb`, `soffit`, `plinth`, `fastener`, `consumable`.
- Экран каталога в приложении подготовлен к переключению категорий.
- В каталоге реализованы локальные фильтры по материалу и цвету, сортировка по названию/цене/категории.
- Экран поиска ищет по названию, описанию, категории, артикулу, материалу и цвету.
- Реализована MVP-смета: добавление товара из карточки, количество, список позиций, удаление, очистка, итоговая сумма, серверное сохранение и загрузка сохраненных смет. Документ: `docs/estimate_mvp.md`.
- Серверная часть на PHP и MySQL уже используется для авторизации и каталога.

### Что нужно доделать в ближайших этапах

- Загрузить в каталог откосы. Подготовительный файл: `docs/catalogs/slopes_catalog.md`.
- Загрузить дополнительные элементы: уголки, затирку, отливы, софиты, подшивку софитов, фронтальные свесы, элементы цоколя, крепеж и расходники. Подготовительный файл: `docs/catalogs/additional_elements_catalog.md`.
- Расширить API каталога, чтобы приложение получало не только панели, но и все дополнительные элементы.
- Доработать карточки материалов, фильтры, выбор параметров и расчет сметы.
- Реализовать личный кабинет пользователя и администратора в полном объеме.
- Реализовать Pro-подписку, оплату, рекламу, калькулятор и заявки.

## 2. Приоритеты разработки

### Приоритет 1. Стабилизация текущей авторизации и каталога

Цель: убедиться, что текущий фундамент работает стабильно перед добавлением новых функций.

Задачи:

- Проверить полный сценарий: новый пользователь -> код `123456` -> регистрация -> сохранение токена -> повторный запуск без авторизации.
- Проверить полный сценарий: существующий пользователь -> код `123456` -> вход -> сохранение токена.
- Проверить, что при сетевой ошибке токен не удаляется автоматически.
- Проверить, что выход из аккаунта очищает токен.
- Проверить CORS-заголовки API для web/debug-сценариев.
- Проверить работу на Android-устройстве, Android-эмуляторе и, отдельно, на iOS при наличии окружения.
- Убедиться, что каталог загружается с боевого API и корректно показывает пустые/ошибочные состояния.

Критерии готовности:

- Пользователь не авторизуется повторно после успешного входа.
- Новый пользователь корректно попадает на регистрацию.
- Существующий пользователь корректно попадает в приложение.
- Каталог открывается без ошибок и не падает при проблемах API.

## 3. Этап 1. Расширение каталога материалов

### 3.1. Подготовка структуры данных

Нужно определить единый формат для всех материалов:

- термопанели;
- откосы;
- уголки;
- затирка;
- отливы;
- софиты;
- подшивка софитов;
- фронтальные свесы;
- элементы для цоколя;
- крепеж;
- расходники.

Для каждой позиции нужно хранить:

- ID;
- название;
- артикул;
- категорию;
- описание;
- материал: пластик, металл, другое;
- цвет;
- фактуру;
- толщину;
- размеры;
- единицу измерения;
- цену;
- изображение;
- статус активности;
- порядок сортировки;
- дату создания и обновления.

### 3.2. Загрузка откосов и дополнительных элементов в БД

Задачи:

- Подготовить список откосов с параметрами, ценами и изображениями.
- Подготовить список дополнительных элементов.
- Добавить недостающие поля в MySQL, если текущей структуры недостаточно.
- Написать SQL-миграцию или скрипт загрузки данных.
- Загрузить изображения в `backend/public/catalog` или другое согласованное хранилище.
- Проверить, что ссылки на изображения открываются по HTTPS.

Проверки:

- все позиции имеют название и цену;
- нет дублей артикулов;
- цена не отрицательная;
- изображение существует;
- отключенные позиции не показываются пользователю;
- сортировка работает стабильно.

### 3.3. Расширение API каталога

Задачи:

- Доработать endpoint каталога, чтобы он отдавал категории материалов.
- Добавить фильтр по категории: панели, откосы, уголки, затирка и т.д.
- Добавить фильтры по цвету, материалу, толщине и активности.
- Добавить единый JSON-формат ответа.
- Добавить обработку пустого результата.

Нюансы:

- Приложение не должно ломаться, если у позиции нет изображения.
- Старый формат каталога лучше сохранить или аккуратно заменить, если текущая версия еще не опубликована.
- Цены должны приходить с сервера, а не быть зашитыми в приложение.

Критерии готовности:

- API возвращает панели и дополнительные элементы.
- Приложение может отдельно запросить откосы.
- Приложение может показать список дополнительных элементов без падений.

### 3.4. Доработка приложения для дополнительных элементов

Задачи:

- Обновить модель каталога в Flutter.
- Добавить отображение категорий.
- Добавить экран/раздел для откосов.
- Добавить разделы для уголков, затирки, отливов, софитов и других элементов.
- Добавить состояния загрузки, ошибки и пустого списка.
- Добавить выбор материала: пластик или металл.
- Добавить выбор цвета, если цвет доступен для элемента.

Проверки:

- список открывается при хорошем интернете;
- показывается ошибка при недоступном API;
- нет падения при пустом списке;
- изображение-заглушка показывается, если фото отсутствует;
- длинные названия не ломают верстку.

## 4. Этап 2. Личный кабинет пользователя

Цель: дать пользователю доступ к своим данным, сметам, заявкам и подписке.

Задачи:

- Реализовать получение профиля пользователя через API.
- Показывать ФИО, телефон, email, статус Pro.
- Добавить редактирование ФИО и email.
- Изменение телефона делать только через повторное SMS-подтверждение.
- Добавить список сохраненных смет.
- Добавить список отправленных заявок.
- Добавить выход из аккаунта.

API:

- `GET /profile`;
- `POST /profile/update`;
- `GET /estimates`;
- `GET /orders`;
- `POST /logout`, если требуется инвалидировать токен на сервере.

Проверки:

- пользователь не видит чужие данные;
- при истекшей сессии открывается авторизация;
- выход удаляет локальный токен;
- редактирование валидирует email и обязательные поля.

Критерии готовности:

- пользователь видит свои данные;
- может выйти из аккаунта;
- может открыть свои сметы и заявки.

## 5. Этап 3. Смета и расчет материалов

### 5.1. Базовая смета

Задачи:

- Создать модель сметы в приложении.
- Добавить выбор термопанелей.
- Добавить выбор откосов и дополнительных элементов.
- Добавить ввод площади фасада.
- Добавить ввод размеров окон/дверей или площади исключений.
- Добавить расчет количества панелей.
- Добавить расчет дополнительных элементов.
- Добавить итоговую стоимость.

### 5.2. Правила расчета

Нужно согласовать и реализовать:

- запас на подрезку;
- округление до упаковки или штуки;
- расчет затирки;
- расчет уголков;
- расчет откосов;
- расчет отливов;
- расчет софитов;
- учет толщины панелей;
- единицы измерения для каждой позиции.

Проверки:

- нельзя вводить отрицательные значения;
- пустая площадь не дает сформировать смету;
- изменение материала пересчитывает итог;
- изменение цены на сервере не ломает уже сохраненную смету;
- в сохраненной смете фиксируется цена на момент создания.

Критерии готовности:

- пользователь может собрать смету из панелей и дополнительных элементов;
- итоговая сумма считается автоматически;
- смету можно сохранить в личном кабинете.

## 6. Этап 4. Заявки

Цель: отправлять сформированную смету администратору.

Задачи:

- Добавить кнопку отправки заявки из сметы.
- Перед отправкой проверить авторизацию и контактные данные.
- Передать на сервер состав сметы, комментарий и данные пользователя.
- Сохранить заявку в БД.
- Показать пользователю статус отправки.
- Отобразить заявку в личном кабинете пользователя.

Статусы заявки:

- новая;
- в работе;
- требуется уточнение;
- обработана;
- закрыта;
- отменена.

Проверки:

- пустую смету нельзя отправить;
- заявка не должна дублироваться при двойном нажатии;
- при ошибке сети показывается понятное сообщение;
- пользователь видит только свои заявки.

Критерии готовности:

- заявка создается на сервере;
- пользователь видит ее в ЛК;
- администратор может ее увидеть и обработать.

## 7. Этап 5. Личный кабинет администратора

Цель: дать администратору управление каталогом, ценами, заявками и пользователями.

Задачи:

- Реализовать вход администратора.
- Реализовать список заявок.
- Реализовать карточку заявки.
- Реализовать смену статуса заявки.
- Реализовать управление каталогом.
- Реализовать добавление и редактирование откосов и дополнительных элементов.
- Реализовать загрузку изображений.
- Реализовать управление ценами.
- Реализовать просмотр пользователей.
- Добавить журнал действий администратора.

Нюансы:

- Админка может быть отдельным веб-интерфейсом.
- Все действия администратора должны проверяться сервером.
- Нельзя доверять скрытым полям формы или данным из клиента.

Проверки:

- обычный пользователь не может открыть админские API;
- изменение цены видно в каталоге приложения;
- отключенный материал пропадает из пользовательского каталога;
- загруженное изображение безопасно и открывается по ссылке.

Критерии готовности:

- администратор управляет заявками;
- администратор добавляет откосы и другие элементы без ручного SQL;
- цены меняются из админки.

## 10. Этап 8. Pro-подписка и SmartCalc

Задачи:

- Добавить статусы Pro в БД.
- Добавить тарифы: 1 месяц, 3 месяца, 6 месяцев, 1 год.
- Добавить управление ценами тарифов в админке.
- Выбрать платежную систему.
- Реализовать оплату.
- Реализовать активацию подписки после подтверждения платежа.
- Реализовать проверку активной подписки на сервере.
- Ограничить Pro-функции для пользователей без подписки.
- Встроить или открыть SmartCalc.

Нюансы:

- Для App Store и Google Play могут потребоваться встроенные покупки Apple/Google.
- SmartCalc может не разрешать встраивание в WebView.
- Если SmartCalc нельзя встроить, нужно открывать внешний браузер или реализовать собственный калькулятор.

Проверки:

- успешная оплата активирует Pro;
- отмененная оплата не активирует Pro;
- повторная обработка платежа не продлевает подписку дважды;
- истекшая подписка закрывает Pro-функции;
- изменение цены не меняет уже купленную подписку.

Критерии готовности:

- пользователь может купить Pro;
- Pro-статус хранится на сервере;
- платные функции доступны только при активной подписке.

## 14. Минимальная версия для первого рабочего релиза

Чтобы быстрее получить рабочую версию, можно выпустить MVP.

В MVP включить:

- авторизацию и регистрацию;
- тестовый SMS-код или реальную SMS-отправку;
- проверку пользователя в БД;
- автологин по сохраненному токену;
- каталог панелей;
- каталог откосов и дополнительных элементов;
- простую смету;
- сохранение сметы;
- отправку заявки;
- простую админку для просмотра заявок и управления ценами.

Во второй релиз перенести:

- сложную примерку панелей на фото;
- расширенную разметку зон фасада;
- Pro-подписку;
- SmartCalc;
- рекламу;
- полноценную аналитику и push-уведомления.

## 15. Контрольный список перед каждым этапом

Перед началом этапа:

- понятно, какие таблицы БД нужны;
- согласован формат API;
- есть тестовые данные;
- понятен экран или пользовательский сценарий;
- определены обязательные проверки.

Перед завершением этапа:

- работает успешный сценарий;
- проверены ошибки сети;
- проверены пустые данные;
- проверены некорректные данные;
- нет падений приложения;
- изменения протестированы на устройстве;
- документация обновлена.
