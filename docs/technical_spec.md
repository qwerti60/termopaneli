# Техническое задание

## 1. Общие сведения о проекте

### 1.1. Назначение продукта

Необходимо разработать кроссплатформенное мобильное приложение для подбора фасадных термопанелей компании. Приложение должно помогать пользователю:

- подбирать цветовые решения и типы фасадных термопанелей;
- примерять панели на фотографию дома;
- рассчитывать ориентировочное количество материалов и стоимость работ/материалов;
- сохранять сметы в личном кабинете;
- отправлять заявку администратору для обратной связи;
- пользоваться расширенными функциями по подписке Pro.

Приложение должно поддерживать Android и iOS. Серверная часть используется для авторизации, хранения пользователей, каталога материалов, цен, заявок, смет, подписок и административных данных.

### 1.2. Целевая аудитория

- частные клиенты, выбирающие фасадные панели для дома;
- менеджеры компании, обрабатывающие заявки;
- администраторы, управляющие каталогом, ценами, пользователями, подписками и заявками.

### 1.3. Основные роли

- Гость: пользователь без авторизации.
- Зарегистрированный пользователь: пользователь с подтвержденным телефоном.
- Pro-пользователь: пользователь с активной платной подпиской.
- Администратор: сотрудник компании с доступом к административной панели.

### 1.4. Платформы

- Android: актуальные версии Android, которые поддерживаются текущей версией Flutter.
- iOS: актуальные версии iOS, которые поддерживаются текущей версией Flutter.
- Административная панель: веб-интерфейс, адаптированный минимум под desktop и tablet.

### 1.5. Технологический стек

- Клиентское приложение: Flutter, Dart.
- Серверная часть: PHP.
- База данных: MySQL.
- Хранение пользовательских изображений: файловое хранилище на сервере или совместимое объектное хранилище.
- Авторизация: SMS-код и серверный токен сессии.
- Платежи: механика должна быть согласована отдельно с учетом правил App Store и Google Play.

## 2. Общая логика приложения

### 2.1. Первый запуск

При первом запуске приложение должно показать экран авторизации или стартовый экран с возможностью перейти к авторизации.

Если пользователь ранее авторизовался, приложение должно:

- прочитать сохраненный токен сессии из локального хранилища;
- отправить токен на сервер для проверки;
- если токен действителен, открыть основной экран без повторной авторизации;
- если токен недействителен, открыть экран авторизации;
- при временной сетевой ошибке не удалять токен автоматически, чтобы пользователь не терял сессию из-за кратковременного сбоя.

### 2.2. Поведение без интернета

Необходимо предусмотреть:

- понятное сообщение при отсутствии интернета;
- запрет действий, которые требуют сервера: вход, регистрация, отправка заявки, оплата, синхронизация смет;
- возможность просматривать уже загруженные локальные данные, если они кэшируются;
- повтор запроса после восстановления соединения.

### 2.3. Основные разделы приложения

- Авторизация и регистрация.
- Каталог термопанелей.
- Подбор и примерка панелей на фото.
- Калькулятор и смета.
- Личный кабинет пользователя.
- Оформление заявки.
- Pro-подписка.
- Рекламные блоки.
- Административная панель.

## 3. Регистрация и авторизация

### 3.1. Авторизация по телефону

Пользователь вводит номер телефона. Приложение должно:

- нормализовать номер к единому формату, например `7XXXXXXXXXX`;
- проверять корректность номера до отправки;
- отправлять запрос на сервер для выдачи SMS-кода;
- показывать пользователю состояние отправки;
- ограничивать частоту повторной отправки кода;
- показывать таймер повторной отправки;
- принимать 6-значный код;
- отправлять номер и код на сервер для проверки.

### 3.2. Проверка пользователя в базе

После ввода корректного SMS-кода сервер должен проверить наличие пользователя в БД:

- если телефон найден, сервер возвращает токен сессии, приложение сохраняет токен и открывает основной экран;
- если телефон не найден, сервер возвращает признак нового пользователя, приложение переводит пользователя на экран регистрации/заполнения данных;
- если код неверный или истек, приложение показывает понятную ошибку;
- если сервер недоступен, приложение показывает ошибку связи и предлагает повторить.

### 3.3. Регистрация нового пользователя

При регистрации новый пользователь должен заполнить обязательные данные:

- фамилия;
- имя;
- отчество;
- номер телефона, подтвержденный SMS-кодом;
- email.

После сохранения сервер должен:

- повторно проверить SMS-код или временный статический код в dev-режиме;
- проверить, что пользователь с таким телефоном еще не зарегистрирован;
- создать запись пользователя;
- создать токен сессии;
- вернуть токен приложению.

Приложение должно сохранить токен и не требовать авторизацию при следующем запуске, пока токен действителен.

### 3.4. Подписка на Telegram-канал при регистрации

При регистрации необходимо предложить пользователю подписаться на канал:

`https://t.me/facade_panel`

Требования:

- показать понятный экран или диалог с предложением подписаться;
- открыть Telegram или браузер по ссылке на канал;
- дать пользователю возможность подтвердить, что он подписался;
- не блокировать регистрацию навсегда, если Telegram не установлен или ссылка не открылась;
- предусмотреть текст ошибки, если не удалось открыть ссылку.

Нюанс проверки подписки:

- Telegram не позволяет надежно проверить подписку обычного пользователя только по номеру телефона.
- Для автоматической проверки нужен Telegram-бот, права администратора бота в канале и привязка Telegram ID пользователя к аккаунту.
- Если автоматическая проверка обязательна, нужно отдельно реализовать сценарий: пользователь открывает бота, нажимает старт, бот передает Telegram ID, сервер проверяет членство в канале через Telegram Bot API.
- Если такой сценарий не внедряется, проверка подписки считается подтверждением со стороны пользователя.

### 3.5. Ограничения и защита авторизации

Нужно предусмотреть:

- лимит повторной отправки SMS;
- лимит неверных попыток ввода кода;
- срок жизни SMS-кода;
- защиту от частых запросов с одного номера и IP;
- логирование ошибок авторизации на сервере без записи SMS-кода в открытом виде;
- невозможность использовать один и тот же одноразовый код бесконечно, кроме явно включенного dev-режима.

### 3.6. Dev-режим SMS

На период разработки допускается временный код `123456`.

Требования:

- dev-код должен включаться настройкой сервера;
- на production dev-код должен быть отключаемым;
- приложение может показывать сообщение, что SMS временно отключены и используется тестовый код;
- даже с тестовым кодом сервер должен проверять наличие пользователя в БД и решать: вход или регистрация.

В личном кабинете пользователь должен видеть:

- ФИО;
- телефон;
- email;

- срок действия подписки;

Пользователь должен иметь возможность изменить:

- ФИО;
- email;
- дополнительные контактные данные, если они будут добавлены.

Изменение телефона должно требовать повторного подтверждения через SMS.

### 4.3. Выход из аккаунта

При выходе:

## 5. Pro-подписка и калькулятор

### 5.1. Pro-функции

Pro-версия должна открывать доступ к расширенным функциям:

- встроенный калькулятор `https://www.smartcalc.ru/`;
- расширенный расчет сметы;
- сохранение расширенных расчетов;
- дополнительные параметры материалов и фасада, если они ограничиваются подпиской.

### 5.1.1 Оформление и ограничения (MVP, фактическое поведение)

- **Одна активная подписка:** повторное оформление через **`POST .../subscription/checkout.php`**, пока не истекла текущая подписка и не выполнена **отмена**, сервером отклоняется (**HTTP 409**, код **`already_subscribed`**). В клиенте кнопка повторной покупки заблокирована; сменить тариф можно после **отмены** активной подписки.
- **Оформление без эквайринга:** до подключения платёжного провайдера успешный checkout создаёт запись подписки и выставляет **`is_pro`**; в журнале событий — **`activated_no_acquiring`**.
- **Задержка обновления профиля:** на устройстве используется кратковременный **локальный grace** (отдельно от сервера), чтобы **SmartCalc** оставался доступен, пока **`GET .../profile/me.php`** не вернёт обновлённый **`is_pro`**; grace сбрасывается при **отмене** подписки и при **выходе** из аккаунта. Подробности и длительности окон — в **`docs/estimate_mvp.md`**, якорь **`#mvp-subscription-pro`**.

### 5.2. Интеграция SmartCalc

**Реализовано в приложении (MVP):** пункт **«SmartCalc»** в личном кабинете открывает экран с **WebView**, если пользователь считается **PRO**: по ответу **`GET .../profile/me.php`** (**`is_pro`**) **или** в пределах локального grace-периода после оформления подписки (см. **§5.1.1**). Начальный URL берётся из **`GET .../settings/app-manifest.php`** → поле **`smartcalc_url`** (на сервере: **`config.php` → `app_manifest.smartcalc_url`**). Типичный адрес сервиса — `https://www.smartcalc.ru/`; конкретный URL задаётся администратором API.

Возможные варианты реализации (исторически):

- WebView внутри приложения;
- открытие внешнего браузера;
- отдельная интеграция через API, если SmartCalc предоставляет API.

Нужно проверить:

- разрешает ли сайт встраивание во WebView;
- корректно ли работает калькулятор на мобильных экранах;
- нет ли блокировок, капчи или ограничений;
- не нарушаются ли условия использования SmartCalc;
- можно ли передавать и получать параметры расчета автоматически.

Если WebView не поддерживается сайтом или работает нестабильно, необходимо использовать внешний браузер либо согласовать альтернативную реализацию калькулятора внутри приложения.

### 5.3. Тарифы

В приложении должны быть доступны периоды подписки:

- 1 месяц;
- 3 месяца;
- 6 месяцев;
- 1 год.

Стоимость каждого тарифа задается администратором в административной панели.

### 5.4. Управление ценами подписки

Администратор должен иметь возможность:

- задать цену для каждого периода;
- включить или отключить конкретный тариф;
- изменить описание тарифа;
- видеть дату последнего изменения цены;
- видеть, кто изменил цену.

Проверки:

- цена не может быть отрицательной;
- цена должна быть числом с допустимой точностью;
- нельзя удалить активный тариф, если на него есть действующие подписки, можно только отключить для новых покупок;
- изменение цены не должно менять стоимость уже оплаченной подписки.

### 5.5. Оплата подписки

Механика оплаты должна быть выбрана с учетом правил магазинов:

- для цифрового функционала внутри iOS-приложения обычно требуется In-App Purchase Apple;
- для Android-приложения из Google Play обычно требуется Google Play Billing;
- внешние платежные системы могут быть ограничены правилами магазинов;
- если приложение распространяется вне магазинов, можно рассмотреть YooKassa, CloudPayments или иной платежный провайдер.

Минимальные требования:

- создание платежа;
- подтверждение успешной оплаты;
- активация подписки только после подтверждения от платежной системы;
- хранение истории оплат;
- обработка отмены оплаты;
- обработка ошибки оплаты;
- обработка возврата, если провайдер это поддерживает;
- защита от повторной активации одной и той же транзакции.

### 5.6. Срок действия подписки

Сервер должен хранить:

- дату начала подписки;
- дату окончания подписки;
- статус подписки;
- выбранный тариф;
- идентификатор платежа;
- сумму оплаты;
- источник оплаты.

Если пользователь покупает подписку повторно до окончания текущей, новая длительность должна добавляться к текущей дате окончания или применяться по согласованному бизнес-правилу.

## 6. Рекламная сеть

### 6.1. Общие требования

В приложение необходимо добавить рекламную сеть.

Возможные варианты:

- Yandex Ads;
- Google AdMob;
- другая рекламная сеть по согласованию.

### 6.2. Форматы рекламы

Необходимо предусмотреть:

- баннеры;
- полноэкранную рекламу между действиями, если это не мешает основному сценарию;
- рекламу с вознаграждением, если будет выбран такой сценарий.

### 6.3. Бизнес-правила показа рекламы

Нужно согласовать:

- показывать ли рекламу Pro-пользователям;
- частоту показа рекламы;
- экраны, где реклама запрещена;
- поведение при отсутствии загрузки рекламы;
- ограничения для экранов оплаты и регистрации.

Рекомендуемое правило: не показывать рекламу на экранах авторизации, регистрации, оплаты и заполнения персональных данных.

### 6.4. Проверки рекламы

Нужно проверить:

- корректную инициализацию SDK;
- отсутствие падений приложения при недоступности рекламной сети;
- соответствие требованиям App Store и Google Play;
- наличие согласия на персонализацию рекламы, если требуется;
- поведение на детских/чувствительных категориях, если они применимы.

## 7. Каталог материалов

### 7.1. Состав каталога

Каталог должен содержать:

- термопанели;
- цвета;
- типы фактуры;
- толщины;
- размеры;
- цены;
- изображения;
- доступность;
- дополнительные элементы.

### 7.2. Параметры термопанели

Для каждой панели необходимо хранить:

- название;
- артикул;
- описание;
- цвет;
- фактура;
- толщина;
- размер;
- единица измерения;
- цена;
- изображение;
- статус активности;
- порядок сортировки.

### 7.3. Дополнительные элементы

Нужно предусмотреть:

- уголки;
- затирку;
- откосы;
- отливы;
- софиты;
- подшивку софитов;
- фронтальные свесы;
- элементы для цоколя;
- элементы для углов;
- крепеж и расходники, если они участвуют в смете.

Для дополнительных элементов должен быть выбор материала:

- пластик;
- металл.

### 7.4. Обновление каталога

Каталог должен загружаться с сервера. Приложение должно:

- показывать индикатор загрузки;
- показывать ошибку при недоступности сервера;
- не падать при пустом каталоге;
- корректно обрабатывать отсутствующие изображения;
- при необходимости кэшировать каталог.

## 8. Загрузка фотографии дома

### 8.1. Источники фото

Пользователь должен иметь возможность:

- сделать фото камерой;
- выбрать изображение из галереи;
- выбрать форму дома из встроенной галереи шаблонов.

### 8.2. Требования к фото

Нужно предусмотреть:

- проверку формата файла;
- ограничение максимального размера файла;
- сжатие перед загрузкой;
- обработку поворота изображения;
- предупреждение при слишком низком разрешении;
- удаление временных файлов, если они больше не нужны.

### 8.3. Разрешения

Приложение должно корректно запрашивать разрешения:

- камера;
- галерея/фото;
- хранилище, если требуется конкретной платформой.

Если разрешение отклонено, приложение должно показать понятное сообщение и возможность перейти в настройки.

## 9. Примерка фасадных термопанелей на фото

### 9.1. Основной сценарий

Пользователь загружает фото дома, выбирает тип и цвет термопанелей, после чего приложение визуально накладывает выбранный материал на фасад.

### 9.2. Выделение областей фасада

Приложение должно позволять выделять и редактировать отдельные элементы:

- основная плоскость фасада;
- цоколь;
- углы;
- стропила;
- софиты;
- подшивка софитов;
- фронтальные свесы;
- отливы;
- откосы на окна.

### 9.3. Инструменты редактирования

Необходимо предусмотреть:

- ручное выделение области;
- изменение границ области;
- отмену последнего действия;
- сброс изменений;
- масштабирование фото;
- перемещение фото;
- сохранение результата.

### 9.4. Реальное время

При выборе цвета или типа панели результат должен обновляться без полной перезагрузки экрана.

Нужно проверить:

- скорость работы на слабых устройствах;
- отсутствие зависаний при больших фото;
- корректность отображения после поворота экрана;
- сохранение выбранных областей после возврата на экран.

### 9.5. Галерея форм домов

Приложение должно содержать набор типовых форм домов. Для каждой формы должны быть заранее определены области фасада, если это технически возможно.

Для шаблонов нужно хранить:

- изображение;
- название;
- тип дома;
- заранее размеченные зоны;
- доступность шаблона.

## 10. Расчет материалов и сметы

### 10.1. Входные данные для расчета

Расчет должен учитывать:

- площадь фасада;
- площадь цоколя;
- размеры окон;
- размеры дверей;
- количество углов;
- длину откосов;
- длину отливов;
- длину софитов;
- выбранный тип панели;
- толщину панели;
- выбранный цвет;
- выбранные дополнительные элементы;
- материал дополнительных элементов;
- расход затирки;
- запас на подрезку и отходы;
- цены из каталога.

### 10.2. Автоматический расчет

Приложение должно рассчитывать:

- количество термопанелей;
- количество затирки;
- количество уголков;
- количество дополнительных элементов;
- ориентировочную стоимость материалов;
- итоговую сумму сметы.

### 10.3. Ручные корректировки

Пользователь или менеджер должен иметь возможность вручную скорректировать:

- площадь;
- количество материалов;
- процент запаса;
- отдельные позиции сметы.

Ручные изменения должны быть явно отмечены в смете.

### 10.4. Проверки расчета

Нужно предусмотреть:

- запрет отрицательных значений;
- проверку пустых обязательных параметров;
- округление количества материалов по правилам упаковки;
- предупреждение, если площадь равна нулю;
- предупреждение, если выбраны несовместимые материалы;
- пересчет сметы при изменении цены или материала;
- сохранение версии цен на момент формирования сметы.

### 10.5. Формирование сметы

Смета должна содержать:

- данные пользователя;
- дату создания;
- выбранные панели;
- цвета;
- толщины;
- дополнительные элементы;
- количество;
- единицы измерения;
- цену за единицу;
- итоговую стоимость;
- комментарий пользователя;
- статус заявки, если смета отправлена администратору.

## 11. Оформление заявки

### 11.1. Создание заявки

Пользователь должен иметь возможность отправить сформированную смету администратору.

Перед отправкой нужно проверить:

- пользователь авторизован;
- телефон подтвержден;
- заполнены обязательные контактные данные;
- смета не пустая;
- сервер доступен.

### 11.2. Данные заявки

Заявка должна содержать:

- ID пользователя;
- ФИО;
- телефон;
- email;
- смету;
- выбранные изображения или ссылки на них;
- комментарий пользователя;
- дату создания;
- статус заявки.

### 11.3. Статусы заявки

Минимальные статусы:

- новая;
- в работе;
- требуется уточнение;
- обработана;
- закрыта;
- отменена.

### 11.4. Уведомления

Нужно предусмотреть:

- уведомление администратора о новой заявке;
- уведомление пользователя об изменении статуса, если будет реализована система уведомлений;
- email или push-уведомления по согласованию.

## 12. Личный кабинет администратора

### 12.1. Доступ администратора

Административная панель должна быть защищена авторизацией.

Требования:

- отдельные учетные записи администраторов;
- пароль или иной согласованный способ входа;
- разграничение прав, если администраторов несколько;
- логирование важных действий.

### 12.2. Управление каталогом

Администратор должен уметь:

- добавлять материалы;
- редактировать материалы;
- загружать изображения;
- изменять цены;
- включать/отключать позиции;
- задавать порядок сортировки;
- управлять дополнительными элементами.

### 12.3. Управление заявками

Администратор должен видеть:

- список заявок;
- карточку заявки;
- контактные данные пользователя;
- приложенные фото;
- состав сметы;
- историю изменения статуса;
- комментарии администратора.

Администратор должен уметь:

- менять статус заявки;
- добавлять комментарий;
- фильтровать заявки по статусу, дате, пользователю;
- искать заявку по телефону или email.

### 12.4. Управление пользователями

Администратор должен видеть:

- список пользователей;
- дату регистрации;
- телефон;
- email;
- статус Pro;
- историю заявок;
- историю смет.

Нужно определить, может ли администратор редактировать данные пользователя или только просматривать.

### 12.5. Управление подписками

Администратор должен видеть:

- активные подписки;
- истекшие подписки;
- историю платежей;
- выбранные тарифы;
- даты окончания подписок.

Администратор должен уметь:

- менять цены тарифов;
- отключать тарифы;
- вручную выдать или продлить Pro-доступ, если это разрешено бизнес-правилами;
- видеть причину ручного изменения.

## 13. Серверная часть и API

### 13.1. Общие требования к API

API должно:

- возвращать JSON;
- использовать единый формат ошибок;
- корректно отвечать на CORS-запросы для web/debug-сценариев;
- поддерживать авторизацию через токен;
- проверять входные данные на сервере;
- не доверять данным, пришедшим из приложения;
- логировать критические ошибки.

### 13.2. Основные endpoint'ы

Минимально необходимы:

- запрос SMS-кода;
- проверка SMS-кода;
- регистрация пользователя;

- обновление профиля;
- получение каталога;
- получение цен;
- сохранение сметы;
- получение списка смет пользователя;
- отправка заявки;
- получение статусов заявок;
- административные endpoint'ы для каталога, заявок, пользователей, подписок и цен.

### 13.3. Безопасность API

Нужно предусмотреть:

- HTTPS;
- хранение токенов в БД в защищенном виде или с достаточной энтропией;
- ограничение срока жизни токена или механизм его обновления;
- защиту от SQL-инъекций через prepared statements;
- ограничение частоты запросов;
- проверку прав доступа на каждом endpoint'е;
- запрет доступа пользователя к чужим сметам и заявкам;
- безопасную загрузку файлов.

## 18. Критерии приемки

Проект считается готовым к приемке, если:

- пользователь может зарегистрироваться и войти по SMS-коду;
- существующий пользователь после повторного запуска попадает в приложение без повторной авторизации;
- новый пользователь после проверки кода попадает на регистрацию;
- каталог загружается с сервера;
- пользователь может выбрать панели и параметры фасада;
- пользователь может загрузить фото или выбрать шаблон;
- приложение позволяет визуально применить выбранные панели к фото или шаблону;
- расчет сметы учитывает выбранные материалы, дополнительные элементы и цены;
- смета сохраняется в ЛК;
- заявка отправляется в ЛКА;
- администратор видит заявки и может менять их статус;
- администратор может управлять каталогом и ценами;
- Pro-подписка открывает платные функции;
- реклама отображается согласно бизнес-правилам;
- приложение стабильно работает на согласованных Android и iOS устройствах;
- персональные данные передаются по HTTPS и защищены от несанкционированного доступа.

## 20. Риски и важные нюансы

- Встраивание SmartCalc может быть ограничено технически или юридически.
- Автоматическая проверка подписки на Telegram-канал невозможна только по номеру телефона без отдельного бота и Telegram ID.
- Для цифровой подписки магазины приложений могут требовать встроенные платежи Apple/Google.
- Реалистичная примерка панелей на фото может потребовать сложной графической обработки и ручной разметки зон.
- Точный расчет материалов зависит от корректных входных данных пользователя и правил округления.
- Реклама не должна мешать критическим сценариям: регистрация, оплата, отправка заявки.
- Dev-код `123456` должен быть отключен на production перед публичным запуском.
- Нужны CORS-заголовки на сервере для Flutter Web/debug-сценариев.
- При сетевой ошибке нельзя автоматически удалять токен, иначе пользователь будет терять авторизацию.
